บทที่ 3 · "ส่ง" — เราส่งโค้ดให้อีกฝั่งยังไง

ดึงจาก Branch เดียว — อย่าไปยุ่งกับ Branch อื่น

# Branch ของ project ตัวเองเท่านั้น git fetch origin delivery/『project』 git checkout delivery/『project』 # README.md ที่ root ของ branch มีรายละเอียดครบ # (module version, ขั้นตอน UAT, ข้อจำกัดที่รู้อยู่แล้ว)
สำคัญ: Repo ต้นทางเป็น repo ที่ MBX ใช้พัฒนาโมดูลอื่นให้ project อื่นด้วย จะเห็น branch อื่นที่ไม่เกี่ยวกับ project ของคุณปนอยู่ — ใช้เฉพาะ branch delivery/『project』 ของตัวเองเท่านั้น
Tag ทุกรอบส่งมอบ
รูปแบบ mxdevlab/『branch』/v『version』 — git tag -l "mxdevlab/*" เห็นทุกรอบที่เคยส่งมา
เลขเวอร์ชัน 19.0.A.B.C
MBX ขยับหลัก B (ฟีเจอร์ใหม่) — ถ้าอีกฝั่งแก้ต่อเอง ให้ขยับหลัก C (hotfix) กันเลขชนกัน
บทที่ 4 · "รับ" — เรารับโค้ดกลับจากอีกฝั่งยังไง

2 รูปแบบ ต่างกันที่ "อีกฝั่งยัง dev คู่ขนานอยู่หรือเปล่า"

Round-trip (ทั่วไป)
ใช้เมื่ออีกฝั่งรับโค้ดไปดูแลต่อเองแล้ว ไม่ได้ dev คู่ขนานกับเราต่อเนื่อง — ดึงกลับเฉพาะตอนถูกสั่งเท่านั้น ไม่บ่อย
Pull-before-dev (กรณีพิเศษ)
ใช้เมื่ออีกฝั่งยัง dev คู่ขนานอยู่จริงบน repo ต้นทางเดิม — ดึงมาก่อนเริ่ม dev รอบใหม่ทุกครั้ง ของ project นั้น (ไม่ใช่รอสั่ง)
เหมือนกันตรงไหน
ทั้งสองแบบ: เปิด branch ใหม่ตั้งชื่อตามวันที่ดึง → รีวิว diff เฉพาะ path ที่เกี่ยวข้อง → เลือก merge เฉพาะจุด ไม่เคย merge ทั้งดุ้นแบบไม่รีวิว
repo ต้นทาง 『branch ของอีกฝั่ง』 ──fetch──▶ เปิดเป็น branch ใหม่ใน MX-DEV-LAB ตั้งชื่อตามวันที่ดึง ──รีวิว diff เฉพาะ path ที่เกี่ยวข้อง──▶ เลือก merge เฉพาะจุด เข้า branch project เดิม
บทที่ 5 · ตัวอย่างจริง — Pull-before-dev ของ MXP

ทำไม "รีวิวก่อน merge เสมอ" ไม่ใช่แค่กฎเฉยๆ

  • 1MXP เป็น project เดียวที่อีกฝั่งยัง dev คู่ขนานบน branch dev ของ repo ต้นทางจริง — ตกลงกันให้ pull ก่อนเริ่ม dev รอบใหม่ทุกครั้ง
  • 2ลองรันรอบแรก: fetch dev → เปิด branch รีวิว → diff เฉพาะ path ของ MXP (27 ไฟล์, +1,113/-104 บรรทัด)
  • 3ส่วนใหญ่ปลอดภัยดี (ฟีเจอร์ใหม่ "Membership Dashboard", โมเดล+migration ใหม่)
  • 4แต่เจอจริง: มี 5 ไฟล์ที่ถูกลบ field ป้องกันข้อมูลข้ามบริษัท (company_id) พร้อมไฟล์ security rule ที่คู่กัน โดยไม่มี migration รองรับ
  • 5ผลจากการ "รีวิวก่อน merge เสมอ": จับได้ก่อน merge เข้าโค้ดจริง — แจ้งกลับไปเช็คกับอีกฝั่งก่อน ไม่ merge ส่วนที่มีความเสี่ยงจนกว่าจะได้คำตอบ
ทำไมเรื่องนี้ถึงสำคัญ: ถ้า merge ทั้งดุ้นโดยไม่รีวิว การเปลี่ยนแปลงแบบนี้จะหลุดเข้า production ทันที — นี่คือเหตุผลที่กฎ "ห้าม merge ทั้งดุ้น" ในบทที่ 4 ไม่ใช่ความระมัดระวังเกินเหตุ แต่เจอปัญหาจริงตั้งแต่รอบทดลองรอบแรก
บทที่ 6 · หลักการสำคัญ

3 ข้อที่ใช้เหมือนกันทั้งฝั่ง "ส่ง" และ "รับ"

แยก branch ตาม project เสมอ
ไม่ว่าจะส่งหรือรับ ไม่เคยรวม sync ผ่าน main เดียว — กันปัญหา repo ปนหลาย project/client เข้าด้วยกัน
รีวิวก่อน merge เสมอ
ทั้ง Round-trip และ Pull-before-dev ไม่มีระบบไหนอัตโนมัติ ต้องเปิด branch แยกรีวิวก่อนทุกครั้ง (ดูตัวอย่างจริงบทที่ 5)
สื่อสารชัดเจนเสมอ
ชื่อ branch/repo/tag ต้องตรงกันทั้งสองฝั่ง — git แก้ปัญหา "branch ไหนของใคร" เองไม่ได้ ต้องมีคนยืนยันนอกระบบเสมอ
สรุป

สิ่งที่ต้องจำ 3 ข้อ

  • 1ส่ง = branch delivery/『project』 + README + tag เท่านั้น — branch อื่นในนั้นไม่เกี่ยวข้อง
  • 2รับ = ไม่เคย merge ทั้งดุ้น รีวิวก่อนเสมอ ไม่ว่าจะเป็น Round-trip (ตามสั่ง) หรือ Pull-before-dev (ก่อน dev ทุกรอบ)
  • 3ทุกอย่างแยกตาม project ชัดเจนเสมอ แม้ repo ต้นทางจะเป็น shared repo ที่มีหลาย project ปนกันก็ตาม
