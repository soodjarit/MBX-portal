Fieldความหมาย

บทที่ 04 · Config Layer — Odoo module mx_rfm

Threshold/Segment เป็น version — ต้อง Activate ก่อนถึงมีผล

Scoring Config Version
Company-scoped (silo ir.rule ต่อบริษัท เพราะจังหวะซื้อไม่เท่ากัน)
ต้องมี threshold ครบ score level 1-5 ทั้ง R/F/M ก่อนกด Activate ได้
Activate แล้ว version อื่นของบริษัทเดียวกันถูก archive อัตโนมัติ — active ได้ทีละ 1 ต่อบริษัท

Priority-ordered: ไล่ทีละแถว แถวแรกที่ range ตรงชนะ (แถวสุดท้ายมักเป็น catch-all)

บทที่ 07 · คนละชั้น คนละความหมาย

"Lost" (Fact) ไม่ใช่ตัวเดียวกับ "Hibernating" (Segment)

Lost — Fact-layer event
เดือนนี้ไม่ซื้อเลย (customer_status='lost') — เป็น event รายเดือน อายุสั้น เดือนหน้าซื้ออีกก็หลุดจากสถานะนี้ทันที

เดือนตัวอย่างจริง (2026-05, Café): 103 คน
Hibernating — RFM Segment
R ต่ำ + F ต่ำ สะสม — เป็น profile ระยะยาว ไม่ใช่ event 1 เดือน

เดือนเดียวกัน: 57 คน — 100% ของ 57 คนนี้เป็น "lost" เดือนนั้นด้วย
ทำไมตัวเลขไม่เท่ากัน: จาก 103 คนที่ "lost" เดือนนั้น มีแค่ 57 คนที่สะสมจนกลายเป็น Hibernating — อีก 46 คนยังเป็น At Risk อยู่ (ยังไม่ตกไปถึงระดับ Hibernating) แม้เดือนนี้จะไม่ซื้อเลยก็ตาม
บทที่ 08 · วิธีรันคำนวณ

รันมือทีละ 4 ขั้น — ยังไม่มี cron อัตโนมัติใน v3

-- 1) Fact: คำนวณทั้งประวัติของบริษัทในรอบเดียว
SELECT rfm.refresh_fact_history(3);

-- 2) Walk-in aggregate ต่อเดือน
SELECT rfm.refresh_unidentified(3, '2026-05-01');

-- 3) Score + Segment ตาม config version ที่ active
SELECT rfm.refresh_interpretation(3, '2026-05-01', <scoring_id>, <segment_id>);

-- 4) Month-over-month migration
SELECT rfm.refresh_transition(3, '2026-05-01', <scoring_id>, <segment_id>);
v1 มี n8n cron รายเดือนอัตโนมัติ (WF-RFM-COMPUTE) — v3 ยังไม่มี. ต้องรันมือทุกเดือน หรือสร้าง n8n workflow ใหม่ผูกกับ 4 คำสั่งนี้ — ยังไม่ได้ทำ เป็น gap ที่ควรพิจารณาถ้าจะใช้งานต่อเนื่องระยะยาว

บทที่ 11 · เชื่อมกับระบบอื่น

Segment ไหลเข้า res.partner แล้วต่อไปยัง CDP-CM

interpretation_customer_month→ cron_sync_rfm_segments (รายเดือน)→ res.partner.rfm_segment→ campaign.segment "Apply RFM Segment"
  • 1res.partner เพิ่ม 5 field: rfm_segment, rfm_r_score, rfm_f_score, rfm_m_score, rfm_snapshot_month — readonly ทั้งหมด เขียนได้ทางเดียวผ่าน cron เท่านั้น
  • 2mx_campaign เพิ่ม depend บน mx_rfm ทางเดียว (RFM ไม่ depend กลับ — ไม่ผิดกฎ independence)
  • 3campaign.segment มี dropdown rfm_segment_helper + ปุ่ม "Apply RFM Segment" ที่เขียน domain [('rfm_segment','=',<เลือก>)] ลง Filter Domain ให้อัตโนมัติ — กัน marketer พิมพ์ domain เองแล้วพิมพ์ผิด
ยังใช้งานจริงไม่ได้จนกว่าจะทำสิ่งนี้ก่อน:
ir_cron_rfm_sync_partner_segments เป็น active=False โดยดีไซน์ และไม่เคยรันเลยสักครั้ง → res.partner.rfm_segment ว่างเปล่าทุกคนตอนนี้ → segment ที่เลือกใน campaign audience builder จะได้ partner_count=0 เสมอจนกว่าจะ activate cron นี้แล้วรันอย่างน้อย 1 ครั้ง
บทที่ 12 · เพิ่มบริษัทใหม่ (VOLTA AV / VIVO Sport)

7 ขั้นตอนมาตรฐาน ก่อนเปิดใช้บริษัทที่ 2/3

  • 1เช็คสัดส่วนบิลที่ระบุตัวตนลูกค้าได้ (ผ่านเกณฑ์ ≥30% แล้วทั้งคู่ — VOLTA 93.6%, VIVO 99.0%)
  • 2SELECT rfm.refresh_fact_history(<company_id>); — คำนวณ Fact ทั้งประวัติ
  • 3รัน recommend_threshold.py เพื่อ propose threshold ของบริษัทนั้น (M มักต้องปรับ log-scale เอง ไม่รับ default ตรงๆ)
  • 4Human review + สร้าง Scoring Config Version ใน Odoo (threshold ครบ 1-5 ทั้ง R/F/M) → Activate
  • 5รัน refresh_interpretation + refresh_transition ทีละเดือนหรือ backfill ทั้งชุด
  • 6เช็ค fill-rate (score 1-5 ควรมีคนอยู่ 5-40% ยกเว้น F=1) + segment coverage ก่อนถือว่าใช้งานได้จริง
  • 7Dashboard เห็นข้อมูลทันทีเมื่อเลือก $company เป็นบริษัทนั้น — ไม่ต้องแก้ query ใดๆ
ก่อนเริ่ม: VOLTA/VIVO ยังใช้ demo data แบบ uniform-random เดิม — ควร regenerate เป็น cohort-based ก่อนเหมือน Café ไม่งั้น F dimension จะไม่มี signal จริงเช่นเดียวกับที่เจอใน v1
บทที่ 13 · สิ่งที่ต้องระวัง

Known Gaps — เช็คก่อนใช้งานจริงหรือแก้ schema ครั้งหน้า

ไม่มี cron รันคำนวณอัตโนมัติรายเดือน (v1 มี n8n cron, v3 ยังไม่ได้สร้างใหม่)
