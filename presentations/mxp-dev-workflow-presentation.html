บทที่ 1 · บริบท

จากพัฒนาแบบไม่มีขั้นตอน → มาตรฐานที่มีกติกาชัดเจน

ก่อนหน้านี้
พัฒนาไม่มีขั้นตอนตายตัว ไม่มี environment แยกทดสอบ/โปรดักชันชัดเจน ทีม test ไม่มีช่องทางแจ้งบั๊กที่เป็นระบบ และไม่มี test case เป็นลายลักษณ์อักษรที่ตามทันโค้ด
ตอนนี้ (v2.0)
แยก 3 environment จริง (DEV/UAT/PROD) + branch protection กันการ push ตรง + GitHub Issue เป็นช่องทางที่ทีม non-technical ใช้แจ้งบั๊ก/ติ๊กผลทดสอบได้เอง + test case เขียนคู่โค้ดทุกครั้งที่เปิด PR
ขอบเขตของ Claude Code: เฉพาะงานฝั่ง repo และ test case เท่านั้น — ไม่สร้าง Odoo instance, ไม่ config server, ไม่ backup/restore, ไม่ deploy เอง (เป็นงานของ Admin ทั้งหมด อย่าแตะไฟล์ config/service บน VPS)

บทที่ 2 (ต่อ) · ทิศทาง 2 ทางสวนกัน

โค้ดวิ่งขึ้น ข้อมูลวิ่งลง — คนละทิศทาง

DEV→ UAT→ PROD โค้ดวิ่งขึ้น
PROD→ UAT→ DEV ข้อมูลวิ่งลง
กติกา refresh ข้อมูล: Admin คัดลอก PROD → UAT ทุกต้นเดือน หรือก่อนรอบทดสอบใหญ่
ห้าม restore ดิบๆ เด็ดขาด — อีเมลและ cron จะยิงหาลูกค้าจริง ทุกครั้งที่ restore ต้อง neutralize เสมอ (odoo neutralize / flag --neutralize): ปิด outgoing mail, ปิด scheduled action, ปิด payment provider, เปลี่ยน DB UUID
บทที่ 3 · Git — โครงสร้าง

Mono-repo เดียว รวม custom addons ทั้งหมด

mbx-addons/ ├── ptj_core/ ├── ptj_journal/ ├── ptj_project/ ├── docs/ │ └── test-cases/ ← test case ที่ Claude Code สร้าง │ ├── ptj_core.md │ ├── ptj_journal.md │ └── ptj_project.md └── .github/ └── ISSUE_TEMPLATE/ ├── bug_report.md ← ฟอร์มแจ้งบั๊ก └── uat_round.md ← checklist รอบทดสอบ
Repo เดียวรวม custom addons ทั้งหมด เพราะโมดูลพึ่งพากันเอง — แก้ข้ามโมดูลใน PR เดียวได้ ไม่ต้อง sync หลาย repo
บทที่ 3 (ต่อ) · Branch — มีแค่ 3 แบบ

feature/xxx → uat → main

feature/xxx (งานย่อย)→ uat (รอทดสอบ)→ main (= Production)
Branchความหมายใครแตะได้
mainโค้ดที่รันบน Production ตอนนี้PR เท่านั้น — ต้อง approve จาก Soodjarit และ Admin
uatโค้ดที่รอทีม test ตรวจPR เท่านั้น — approve 1 คนพอ
feature/<ชื่องาน>งานหนึ่งชิ้น เช่น feature/ptj-core-approve-flowDev สร้าง/ลบอิสระ
hotfix/<ชื่อ>แก้ด่วนของ Production แตกจาก mainเฉพาะกรณีฉุกเฉิน
ตั้งค่า GitHub ครั้งเดียว: Branch protection ที่ main (require 2 approvals) และ uat (require 1 approval) → ห้าม push ตรง · ทุก release ที่ขึ้น PROD ติด tag เช่น v19.0.1.3.0 เพื่อ rollback ได้ทันที
บทที่ 4 · Flow หลัก — รอบพัฒนา

จาก feature branch จนถึง PR เข้า uat

  • 1Dev แตก branch feature/xxx จาก uat
  • 2เขียนโค้ดร่วมกับ Claude Code → ทดสอบใน DEV → แก้จนขึ้น module สะอาด
  • 3Claude Code เขียน/อัปเดต test case ใน docs/test-cases/<module>.md ไปพร้อมกับโค้ด
  • 4commit ย่อยๆ พร้อมข้อความสื่อความหมาย → เปิด PR เข้า uat พร้อมระบุว่า "แก้อะไร ต้องทดสอบตรงไหน"
  • 5Admin merge + deploy UAT + เปิด Issue "UAT Round" ประจำสัปดาห์
บทที่ 4 (ต่อ) · รอบทดสอบ → รอบขึ้นจริง

Test Team ตรวจบน UAT ก่อนเปิดทางเข้า PROD

รอบทดสอบ
  • 6Test Team ทดสอบบน UAT ตาม checklist ใน Issue — ผ่าน ติ๊ก checkbox, ไม่ผ่าน เปิด Bug Issue แยก 1 ใบ/1 บั๊ก แล้วกลับไปข้อ 1
รอบขึ้นจริง
  • 7ผ่านครบ + ไม่มีบั๊ก Blocker/Major → เปิด PR uat → main
  • 8Admin backup PROD → merge → git pull ที่ /opt/odoo/prod/addons → -u <module> → restart → ติด tag → smoke test 30 นาที
  • 9ถ้าพัง → rollback ไป tag ก่อนหน้า + restore DB (ต้องซ้อมอย่างน้อย 1 ครั้งก่อนใช้จริง)
บทที่ 4 (ต่อ) · Hotfix (เร่งด่วน)

แก้ด่วนโดยไม่ทิ้งกติกา

main→ hotfix/xxx→ ทดสอบเร็วบน UAT→ merge → main→ merge กลับ → uat
ข้อนี้ลืมบ่อยที่สุด: merge กลับเข้า uat ด้วยเสมอ — ไม่งั้นบั๊กเดิมจะกลับมาในรอบถัดไป เพราะ uat ไม่มีการแก้ที่เพิ่งทำใน hotfix
ไม่ต้องรอรอบ deploy ปกติ แต่ยังต้องผ่าน UAT เสมอ อย่างน้อยแบบ smoke test — ห้ามแก้ตรงบน PROD เด็ดขาด

บทที่ 7–8 · ระดับความรุนแรง & กติกาเฉพาะ Odoo

Blocker หยุด release / กติกา 5 ข้อบังคับที่ห้ามฝ่า

Blocker
ทำงานต่อไม่ได้ / ข้อมูลเสียหาย → หยุด release
Major
ฟีเจอร์หลักใช้ไม่ได้ แต่มีทางเลี่ยง → ต้องแก้ก่อนขึ้น PROD
Minor
ข้อความ/หน้าตา/ความสะดวก → เก็บรอบหน้าได้
  • 1ห้ามแก้อะไรบน PROD ผ่านหน้าจอ — view/field/automation/security ทุกอย่างต้องมาจากโมดูลใน git
  • 2Deploy ใช้ -u <module> เท่านั้น ห้าม -u all บน PROD
  • 3bump version ใน __manifest__.py ทุกครั้ง ไม่งั้น Odoo ไม่ upgrade ให้
  • 4Config ที่ต้องเหมือนกันทุก env ทำเป็น XML data file ในโมดูล ไม่กรอกมือทีละ env
  • 5ห้าม commit odoo.conf, รหัสผ่าน, ไฟล์ backup, .pyc — ตั้ง .gitignore ตั้งแต่วันแรก

บทที่ 10 · Git เท่าที่ต้องใช้จริง

3 คำที่ต้องเข้าใจ: commit / push / pull request

# เริ่มงานใหม่ทุกครั้ง — ดึงของล่าสุดก่อนเสมอ git checkout uat git pull # แตกกิ่งงานใหม่ git checkout -b feature/ptj-core-approve # บันทึกงาน git add . git commit -m "ptj_core: เพิ่มขั้นอนุมัติระดับ 2" # ส่งขึ้น GitHub → ไปกด "Compare & pull request" บนเว็บ git push -u origin feature/ptj-core-approve
commit = บันทึกจุดย้อนกลับไว้ในเครื่องตัวเอง · push = ส่งขึ้น GitHub ให้คนอื่นเห็น · pull request (PR) = ขอรวมงานเข้า branch หลัก และเป็นจุดที่คนอื่นตรวจงาน — เจอ conflict อย่าเดา ให้ Claude Code เปิดไฟล์นั้นแล้วแก้ทีละจุด

บทที่ 11 (ต่อ) · เริ่มใช้จริง

งานตั้งต้นก่อนเริ่มใช้ workflow นี้จริง

  • 1Admin สร้าง instance DEV + UAT แยก config/port/service/filestore
  • 2สร้าง repo mbx-addons ย้ายโมดูลเดิมเข้า + ตั้ง .gitignore
  • 3ตั้ง branch protection main (2 approvals) และ uat (1 approval)
  • 4สร้าง .github/ISSUE_TEMPLATE/ 2 ไฟล์ (bug_report, uat_round)

  • 6Admin ทดลอง restore + neutralize PROD → UAT หนึ่งรอบ
  • 7ซ้อม rollback หนึ่งรอบ ก่อนใช้จริง
  • 8ประชุมทีม 1 ชม. อธิบายเอกสารนี้ + สอนทีม test เปิด Issue
